第 1 节：推理到底是什么？

大模型的一生分两段：

  • 训练：像学生上学。喂给模型海量文字，不断调整它内部的几十亿个参数，让它学会语言规律。花钱多、时间长，一般只做一次或少数几次。
  • 推理：像学生毕业后上班。参数已经固定，你提一个问题，它根据学到的规律给出回答。你每次和 ChatGPT 聊天，都是一次推理。
一句话：推理 = 用训练好的模型，根据输入生成输出。训练决定模型有多聪明，推理决定它回答得多快、多便宜、能同时服务多少人。

为什么推理很重要？因为一个模型训练一次，却要被几亿人调用无数次。推理成本往往才是公司长期最大的开销，所以「推理优化工程师」很吃香。

第 2 节：Token，模型眼里的「字」

模型不直接认识汉字或单词，它先把文字切成小块，叫 token。一个 token 可能是一个字、半个词或一个标点。

比如「我爱人工智能」可能被切成：我爱人工智能

每个 token 会对应一个编号，再变成一串数字（向量），模型才能计算。

为什么要懂 token？因为大模型的计费、速度、长度上限都按 token 算。「上下文 128K」就是最多能装下约 12.8 万个 token。中文里大约 1 个汉字对应 1～2 个 token，具体看分词器。

第 3 节：模型是一个字一个字「蹦」出来的

大模型的核心工作方式叫自回归生成：每次只预测下一个 token，把它接到后面，再预测下一个，循环往复，直到生成结束标记。

输入：今天天气
→
预测：很
→
今天天气很
→
预测：好
→
……

这就是为什么聊天机器人的回答是一点一点「打」出来的：它真的在一个一个算。

重点：生成 100 个字，模型就要完整跑约 100 次。这是推理慢的根本原因，后面的优化几乎都在解决这个问题。

第 4 节：采样，下一个字怎么选？

模型每一步不是直接给出一个字，而是给出所有候选 token 的概率。比如「今天天气」后面：很 50%、不 25%、真 15%、糟 10%。然后用某种规则挑一个，这叫采样。

参数大白话效果
Greedy（贪心）永远选概率最高的稳定，但容易啰嗦重复
Temperature（温度）调节「胆子大小」低温更保守准确，高温更有创意也更容易乱说
Top-k只在前 k 个候选里挑砍掉离谱的低概率选项
Top-p只在累计概率达到 p 的候选里挑候选数量随情况自动变化，更灵活

动手试：拖动温度，看概率怎么变

温度 = 1.0

温度越低，最高的选项越突出；温度越高，各选项越平均。写代码、做数学用低温；写故事、头脑风暴可以调高。

第 5 节：推理的两个阶段，Prefill 和 Decode

Prefill 预填充
一次性读完整个问题
→
吐出第 1 个字
→
Decode 解码
一个字一个字往后生成
  • Prefill：把你输入的所有 token 并行处理一遍。GPU 很擅长并行，所以这一步算力用得很满，属于计算密集型。
  • Decode：每次只生成 1 个 token，却要把整个模型的参数从显存搬出来一遍。大部分时间花在「搬数据」上而不是「算」，属于访存密集型（受显存带宽限制）。
比喻：Prefill 像老师一次性看完整张试卷；Decode 像一笔一划写答案，每写一个字都要重新翻一遍厚厚的课本。

第 6 节：KV Cache，推理最重要的优化

回顾注意力机制：生成新字时，模型要回头「看」前面所有的字。每个字在计算中会产生两组中间结果，叫 K（Key） 和 V（Value）。

问题：如果不做优化，每生成一个新字，前面所有字的 K、V 都要重算一遍，越往后越慢。

解决：把算过的 K、V 存起来，下次直接用，只为新字计算一次。这块缓存就叫 KV Cache。

代价：用显存换速度。KV Cache 会随「对话长度 × 同时服务人数」不断变大，长对话时甚至比模型本身还占显存。所以显存往往是推理的头号瓶颈。

第 7 节：怎么衡量推理快不快？

指标含义用户感受
TTFT（首 token 延迟）从发出问题到看到第一个字的时间「它多久开始回答」
TPOT / ITL（每 token 耗时）后续每个字之间的间隔「字打得快不快」
吞吐量整台服务器每秒总共生成多少 token老板关心：一台机器能服务多少人
并发数同时在处理多少个请求高峰期会不会卡

TTFT 主要受 Prefill 影响，TPOT 主要受 Decode 影响。

延迟和吞吐常常互相矛盾：一次塞更多请求，总吞吐上去了，但每个人可能等得更久。推理优化就是在两者之间找平衡。

第 8 节：推理的三大瓶颈

  1. 显存容量：模型参数 + KV Cache 都要放进 GPU 显存。粗算：参数用 FP16 存储时，每 10 亿参数约占 2GB，7B 模型光参数就约 14GB。
  2. 显存带宽：Decode 阶段每生成一个字都要把参数读一遍，读得越快，字吐得越快。
  3. 计算能力：Prefill 和大批量请求时，GPU 算力会成为限制。

记住这个对应关系，后面每种优化你都能说清它解决的是哪个瓶颈。

第 9 节：批处理，一次服务很多人

Decode 时 GPU 算力大部分在闲着，等数据搬运。那就让它一次处理多个用户的请求，参数只读一遍，同时算好几个人的下一个字，这叫批处理（Batching）。

  • 静态批处理：凑齐一批一起开始、一起结束。问题是有人回答 10 个字，有人回答 1000 个字，短的得陪长的等。
  • 连续批处理（Continuous Batching）：每生成一步就检查一次，谁结束了就立刻让出位置给新请求。像公交车随时上下客，而不是坐满才发车、全员到站才下车。吞吐量可以大幅提升，是现代推理框架的标配。

第 10 节：量化，让模型「瘦身」

模型参数本来用 16 位小数（FP16/BF16）存储。量化就是改用更少的位数，比如 8 位或 4 位整数。

精度7B 模型参数约占显存特点
FP16 / BF16约 14 GB原始精度
INT8 / FP8约 7 GB精度损失通常很小
INT4约 3.5 GB能在普通显卡甚至笔记本上跑，精度有一定损失

表中只算参数本身，实际运行还要加上 KV Cache 和其他开销。

好处一举两得：省显存，而且要搬运的数据变少，Decode 也会更快。常见方法有 GPTQ、AWQ，以及本地运行常用的 GGUF 格式。

比喻：把高清照片压缩成小图，大多数时候看不出区别，但压得太狠就会糊。

第 11 节：更多加速技巧（了解即可）

PagedAttention：像操作系统一样管理 KV Cache

以前每个请求要预留一大块连续显存放 KV Cache，用不完就浪费。PagedAttention 把它切成小「页」按需分配，显存浪费大大减少，能同时服务更多人。这是 vLLM 的核心技术。

FlashAttention：更聪明地算注意力

重新安排计算顺序，减少 GPU 在慢速显存和高速缓存之间来回搬数据，注意力计算更快、更省显存，长文本时效果尤其明显。

投机解码（Speculative Decoding）：小模型打草稿，大模型批改

先让一个又小又快的模型一口气猜出几个字，再让大模型一次性验证。猜对的直接用，猜错的从错误处重来。输出质量不变，速度常能提升明显。

前缀缓存（Prefix Caching）

很多请求开头相同，比如同一段系统提示词。把这部分的 KV Cache 存起来复用，就能省掉重复的 Prefill，降低首字延迟。

模型并行：一张卡放不下怎么办

张量并行把每一层拆到多张卡上一起算；流水线并行把不同层放在不同卡上，像工厂流水线。超大模型推理必须靠多卡。

PD 分离（Prefill / Decode 分离）

Prefill 吃算力，Decode 吃带宽，特点不同。把两者放在不同机器上分别优化，可以同时改善首字延迟和吞吐，大规模在线服务中越来越常见。

第 13 节：面试怎么答

Q：Prefill 和 Decode 有什么区别？（30 秒版）

Prefill 并行处理全部输入，计算密集，决定首 token 延迟；Decode 每次生成一个 token，需要反复读取参数和 KV Cache，访存密集，决定生成速度。

Q：KV Cache 是什么？有什么代价？

缓存已计算 token 的 Key 和 Value，避免每步重复计算，把生成从反复重算变成增量计算。代价是显存占用随序列长度和并发数线性增长，需要用 PagedAttention、量化或前缀复用等手段管理。

Q：为什么连续批处理能提升吞吐？

Decode 阶段 GPU 算力利用率低，批处理能让一次参数读取服务多个请求。连续批处理按步调度，请求结束立即补入新请求，避免短请求等长请求造成空转。

Q：如何降低一个推理服务的成本？

先测指标定位瓶颈；然后可以用量化减少显存和带宽压力，用连续批处理和 PagedAttention 提升并发，用前缀缓存减少重复计算，用投机解码加速生成，必要时把简单请求路由到小模型。

第 14 节：自测题

1. 为什么模型生成长回答比短回答慢？

自回归生成，每多一个 token 就要多跑一次模型。

2. 写代码时温度应该调高还是调低？

调低，让输出更确定、更少出错。

3. 首字很慢、后面很快，大概率是哪个阶段的问题？

Prefill，常见原因是输入太长或排队等待。

4. KV Cache 用什么换了什么？

用显存换速度。

5. 7B 模型用 INT4 量化后，参数大约占多少显存？

约 3.5GB（7B × 0.5 字节），不含 KV Cache 等开销。
